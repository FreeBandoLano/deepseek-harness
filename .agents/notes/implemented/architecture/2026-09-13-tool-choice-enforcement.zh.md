# Agent Note: 被强制的轮次会响亮失败，而不是以文字作答

Status: implemented

[English](2026-09-13-tool-choice-enforcement.md) | 中文

## 问题

把工具选择带到请求体，只让提供方看见要求；它并不让要求生效。网关可以无视该字段，模型也可以照旧以文字作答，而在本次改动之前，这样的响应就是一次普通的成功：调用方要的是一次调用，拿到的是一段文字，且无从得知该要求已经被丢掉。这正是整个特性要消除的失败模式，只是又向外了一层。

有两种相邻事实不能与它混为一谈。被输出上限截断的响应根本没走到调用，把它报告成“无视要求”，会让一个本可被强制的推理模型看起来无法强制——这一误读在探测路由时已经发生过一次。而完全没有产出任何内容的 completion 早已是一种有类型的空响应失败，那是另一种退化情形。

## 决定

当请求声明了工具选择、而终止性 `stop` 携带内容却没有工具调用时，pi-ai 流转换器把它归类为携带新规范 code `TOOL_CHOICE_UNMET` 的 `finish { kind: 'error' }`（`packages/llm/llm/src/error.ts`）。失败消息会点名所欠的东西：当选择指定了函数时点名该函数，否则点名要求本身。

该归类位于 `mapStopReason`（`packages/llm/llm-pi-ai/src/stream.ts`），紧挨着它所扩展的空响应映射，并把请求声明的选择作为第三个参数经 `toStreamChunks` 传入。该函数里有两处顺序属于决定本身：检查只读取 `stop` 这一结束原因，因此 `length` 仍报告 `max-tokens`；检查排在空内容检查之后，因此退化 completion 仍报告 `EMPTY_RESPONSE`。

该 code 有意不出现在 `DEFAULT_RETRYABLE_CODES`（`packages/llm/llm/src/retry-policy.ts`）中。瞬态重试策略重复的是“这次尝试没有留下任何持久产物”的请求；而这次尝试产出的是一个拒绝该要求的回答，因此重试等于向同一个模型问同一个问题，并应当预期同一次拒绝。

失败之所以能原样抵达委派方，是因为进程内一次性驱动现在会从子会话终止性的 `turn/end` 失败中撰写 `SubagentResult.diagnostic`——code 与 message——并受该 seam 既有的 4 KiB 限制器约束；该限制器为此被导出复用。在此之前，每个失败的进程内子会话只报告 `subagent run failed` 加上部分输出，于是编排方能看到“有东西失败了”，却看不到被无视的是哪一项要求。

## 曾考虑的替代方案

**把文字作答转成带警告的成功消息。** 否决：那是换了外衣的静默降级。如果被强制与未被强制的回答都以普通消息抵达，调用方无法区分二者，而那条警告会落在没有编排方读取的地方。

**重试同一请求。** 按上述理由否决：内容失败不是瞬态失败，而对一个无视要求的模型做重试循环，会把一次浪费的调用变成好几次。

**并入既有的 `EMPTY_RESPONSE` 失败。** 否决：空 completion 与文字作答是两种事实，修法也不同——前者是值得重试的提供方抖动，后者是模型拒绝该要求。合并还会让空情形变得不可重试，并掩盖究竟发生了哪一种。

**在适配器而不是转换器里归类。** 否决：转换器已经拥有终止性结束的词汇，包括相邻的空响应用例；再设第二个归类点就得重新推导“什么算一次工具调用”。

**用模型实际发起的调用去匹配被点名的函数。** 未实现：要求是“发生一次调用”，这正是工具选择字段向提供方提出的东西。当具名选择请求了某个工具、而响应调用了另一个工具时，当前实现予以接受；要补上这一点，需要先就“具名选择对只报告‘某工具被调用’的网关意味着什么”作出独立决定。

## 影响

声明了工具选择的 agent 现在会让该轮失败，而不是接受文字作答；委派方会在子会话的部分输出旁边收到这次有类型的失败——code 与 message。

每个失败的进程内子会话现在都带有 diagnostic，不只是被强制的那些。这扩大了委派方可见的内容：此前只有进程外后端能得到提供方失败文本，现在进程内调用方同样能得到，并受同一上限约束。

仍有两处缺口，各自单独跟踪。协议结构上无法承载该字段的路由，是否应在请求之前就被拒绝，是一个独立的决定；在它落地之前，这类路由上的 `toolChoice` 是静默不被强制，而不是响亮地出错。此外，该选项的具名函数形式目前只被强制为“发生了一次调用”。

## 测试

`packages/llm/llm-pi-ai/tests/adapter.spec.ts` 让真实运行时与真实 SDK 跑在仓库内的 mock 端点上：被强制的文字作答以 `TOOL_CHOICE_UNMET` 失败并点名所要求的函数，同一 completion 在未被强制时仍是成功，被上限截断的 completion 仍是 `max-tokens`，完全没有产出的 completion 仍是 `EMPTY_RESPONSE`，而调用了工具的 completion 仍是 `tool-calls`。`packages/subagent/tool-subagent/tests/tool-choice-wire.spec.ts` 在委派 seam 上重复这一对，并断言委派方在失败文本中收到该要求。`packages/llm/llm-retry/tests/retry.spec.ts` 断言该失败在默认策略下不会被重试。
